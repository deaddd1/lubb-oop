# Документ передачі: Ітерація 1 (Lab 34)

## Що вже реалізовано та працює
* Повністю розгорнуто архітектурну структуру проєкту за канонами Clean Architecture.
* Створено ядро доменної моделі (`MenuItem`, `Order`, `OrderItem`) з інкапсуляцією та повним захистом внутрішнього стану (валідація в конструкторах та методах).
* Реалізовано контракт інфраструктури `IOrderRepository` та його In-Memory версію.
* Створено `OrderApplicationService` для управління бізнес-сценаріями.
* Написано та успішно виконуються 5 юніт-тестів, які захищають логіку розрахунку вартості та правила додавання позицій.
* Налаштовано консольне UI-меню, що реалізує наскрізний вертикальний зріз: відкриття замовлення для столу, наповнення стравами, автоматичний калькулятор суми та закриття чека.

## Сценарії для розширення на наступному етапі (Lab 35)
1. Реалізація стійкого збереження даних у фізичні файли на диску через JSON серіалізацію.
2. Створення аналітичного модуля на основі LINQ-запитів для шеф-кухаря та директора ресторану.
3. Додавання Use Case для управління каталогом страв (динамічне меню).

## Класи, свідомо підготовлені під майбутнє розширення
* Інтерфейс `IOrderRepository` — спеціально створений як абстракція, щоб на наступній лабораторній замінити In-Memory колекцію на файловий репозиторій без жодної зміни у бізнес-сервісах (Принцип LSP та DIP).
* Поле `Status` в класі `Order` — наразі є рядком, але спроєктоване так, щоб на Lab 35/36 безболісно впровадити об'єктний патерн State або ієрархію статусів кухні.
